## 1. 평가 세트 형식 (version "1")

JSON Schema: `schemas/evalset.v1.schema.json` (코드의 모델에서 생성, 시험이 일치를 확인). 형식:

```json
{"version": "1", "name": "세트 이름",
 "prompts": [
  {"id": "a01", "lang": "ko|en", "tier": "A|B|C", "text": "프롬프트 문장",
   "expect": {"tonic": "C", "mode": "major", "tempo_bpm": 70, "time_signature": "4/4", "bars": 12, "instruments": ["piano", "drums"], "genre": ["jazz"]}}
 ]}
```
- `id`: 세트 안에서 유일(`[A-Za-z0-9_.-]`, 64자 이하). `lang`·`tier`는 필수. 층(A/B/C)의 뜻은 세트 작성자(연구 1팀)가 정한다 — 하네스는 집계 단위로만 쓴다.
- `expect`(정답 라벨)는 **프롬프트에 글자로 적힌 속성만** 넣는다. 전부 선택이다. 라벨이 없는 항목은 그 지표가 **`na`(해당 없음)** 가 되어 분모에서 빠진다. 무드·장르·음악성은 라벨 필드가 없다(자동 채점 대상이 아님).
- `tonic`은 사양의 `Tonic` 값(이명동음 `C#`/`Db`는 같은 음으로 비교), `mode`는 `Mode` 값, `instruments`는 사양의 `Instrument` 값 + `drums`, **`genre`(v0.4, 선택)는 Intent v1 의 장르 enum 10종(`pop, rock, jazz, blues, ballad, bossa_nova, electronic, ambient, classical, lofi`)의 목록(1~3개, 중복 없음)**. `genre` 가 없는 세트는 이전과 똑같이 동작한다(하위호환). 지금은 음계 이탈 한도(`scale_deviation`)에만 쓰이고, 장르 일치(3-4)는 대기 항목이라 구현하지 않았다.
- 알 수 없는 필드, 범위 밖 값, 중복 id, 빈 세트는 **거부**한다(종료 코드 2, 문제 목록 출력).
- **보류 세트**: 개발 1팀은 보류분을 열지 않는다(합의안 8절). 하네스는 세트 **파일 경로를 인자로 받을 뿐**이며 보류 파일을 레포에 두지 않는다. `.gitignore` 에 `data/eval/holdout*` 가 들어 있어 실수로 올라가는 것을 막는다. 최종 점수는 1회만 잰다(연구 1팀 규칙).

## 2. 지표 (pass / fail / na)

모든 지표는 `pass`, `fail`, `na` 와 사유 문자열을 낸다. **집계의 분모 = pass + fail.** `na` 는 분모에서 빼고 따로 개수만 적는다. 생성 자체가 실패한 프롬프트는 라벨이 있는 지표와 유효성 지표에서 `fail`(사유 "생성 실패")이다 — 시스템이 요구를 못 채운 것이므로 분모에 남긴다. 라벨이 없으면 생성이 실패해도 `na`.

| 지표 (코드 이름) | 무엇을 보나 | 합격 판정 | 해당 없음(na) | 한계 |
|---|---|---|---|---|
| 템포 일치 `tempo_match` | MIDI 첫 `set_tempo` 의 BPM 과 `expect.tempo_bpm` | 기본: 차이 ≤ 0.5 BPM. 옵션 `--tempo-tol 0.10`: 라벨 대비 상대 오차 ≤ 10% (신경망 비교용, 기본으로 켜지 않음, 실행한 허용오차는 summary 머리에 기록) | 라벨 없음 | 곡 중간 템포 변화는 보지 않음. 라벨은 정수 BPM. text2midi 실측은 10곡 중 9곡이 121.3 BPM 이라 신경망 템포 점수는 참고치로만 본다(연구 1팀) |
| 조성 선언 일치(사양 추출) `key_match` | **사양에 선언된** 조성(`key.tonic`, `key.mode`)과 라벨 | 라벨이 있는 필드(tonic, mode)가 모두 일치. tonic 은 이명동음 동일 처리 | tonic·mode 둘 다 없음 | 생성된 음을 분석한 조성이 아니라 선언값이다(컴파일러가 선언 음계 안에서만 쓰는 구조의 효과). text2midi 의 '자동 추정'과 같은 조건이 아님 |
| 박자표 일치 `time_signature_match` | MIDI 첫 `time_signature` 메타와 라벨(`"4/4"`) | 문자열 동일 | 라벨 없음 | 박자 변화는 보지 않음 |
| 마디 수 선언 일치(사양 추출) `bars_match` | 사양의 전체 마디 수(섹션 합)와 `expect.bars` | 동일 | 라벨 없음 | 반복·인트로 등 구조 해석은 하지 않음 |
| 길이 규칙 `bars_min` | bars 를 **명시하지 않은** 프롬프트의 마디 수 | ≥ 8마디 (합의안 Q3: 기본 12, 최소 8). 12 와 다르면 사유에 "(기본 12마디와 다름)"만 적고 판정은 8 기준 | bars 라벨이 있는 프롬프트(그쪽은 `bars_match`) | 초 단위 길이는 템포·박자에 따라 달라 이 지표에 넣지 않음 |
| 악기 선언 일치(사양 추출) `instruments_included` | 라벨 악기가 사양 트랙의 악기(`drums` 는 드럼 트랙 존재)에 모두 들어 있나 | 라벨의 모든 항목이 존재 | 라벨 없음 | **사양 기준**이다. MIDI 프로그램 번호를 직접 읽지는 않음. 라벨에 없는 악기가 더 있어도 감점하지 않음 |
| 악기 포함(MIDI) `midi_instruments_included` | 라벨 악기가 **MIDI 의 프로그램 체인지**(음이 있는 채널)와 드럼 채널에 모두 있나. 연구 1팀 3-7 | 라벨의 모든 항목이 존재 | 라벨 없음 | 프로그램 번호→악기는 17종 GM 매핑만. 같은 프로그램을 쓰는 다른 악기는 구분 못 함 |
| 음계 이탈음 `scale_deviation` | **라벨의** 조(tonic+mode) 음계 밖 음표 비율(드럼 채널 제외). 연구 1팀 2-3 | 기본 ≤ 10%. **세트 항목의 `genre` 라벨에 `jazz` 또는 `blues` 가 있으면 ≤ 25%**(연구 1팀 결정, 평가_기준_초안 2-3; 사유에 "(재즈·블루스 완화 25%)" 표기, 프리셋은 바꾸지 않음) | tonic·mode 라벨 중 하나라도 없음, 음높이 있는 음표 없음 | 경과음·장식음 감안 없음(모든 음표 동일 가중). 재즈·블루스 25% 완화 규칙은 장르 라벨이 없어 미적용. 라벨 조가 틀리면 실패하므로 `key_match` 와 함께 읽는다 |
| 악기 음역 `pitch_range` | 악기(채널의 GM 프로그램)별 음역 밖 음표 비율. 연구 1팀 1-2 | ≤ 5% | 음높이 있는 음표 없음 | 음역표(`INSTRUMENT_RANGE`)의 일부 값은 출처 미확인 근사다(spec.py 주석). 0~127 범위는 파서가 먼저 거른다(1-1) |
| 음 짝·길이 `note_integrity` | NoteOn/NoteOff 짝, 길이 0 음, 닫히지 않은 음, 깨진 트랙. 연구 1팀 1-3 | 위반 0개 | 없음 | MidiCheck 는 길이 0 음을 *경고*로만 보므로 여기서 실패로 센다. 벨로시티 1~127 은 파서가 0~127 밖을 받지 않아 별도 검사 없음 |
| 빈 트랙 없음 `no_empty_tracks` | 템포·박자 트랙이 아닌데 음표가 없는 트랙. 연구 1팀 1-8 | 0개 | 없음 | 트랙 이름·역할까지는 보지 않음 |
| MidiCheck 유효 `midicheck_valid` | 생성된 MIDI 에 `check_midi` **오류** 0건(경고 제외). 파싱·헤더, 템포·박자표 이벤트 존재와 사양 일치, 길이가 사양 마디와 일치, 드럼 채널 일치를 포함 | 오류 0건 | 없음(항상 적용) | 구조 유효성이지 음악적 타당성이 아님 |
| 결정성 `deterministic` | 같은 입력·같은 공급자로 2회 생성한 MIDI 바이트 동일 | 동일 | 생성 실패(비교할 바이트 없음) | 같은 프로세스·같은 의존성 버전 안에서의 확인. 다른 해시 시드 프로세스는 `tests/test_compiler.py` 가 따로 본다 |

### 곡 지표와 사양 추출 지표 (v0.3 분류)
같은 '라벨과 맞나' 질문이라도 **무엇을 재는지**가 다르다. 곡(MIDI)을 재는 지표는 축 1·2·3 으로 집계하고, **사양에 적힌 값**을 재는 지표(`key_match`, `bars_match`, `instruments_included`)는 '사양 추출 일치' 절에 따로 모은다. 요약의 표시 이름에는 '(사양 추출)'을 붙이며 CSV 열 이름은 그대로다. 판단 근거와 전체 표는 7절 끝.

### 참고 열 (합격 판정 아님)
- `attempts`, `retries`(= 시도 − 1), `fallback_used`: 재시도·폴백 여부. 요약에는 그룹별 개수만 적는다. 기본은 폴백 **끔**이라 숫자가 선택한 공급자 단독의 성능이다(`--fallback` 으로 켬).
- `generated`, `error`, `bars`, `midi_sha8`, `provider_used`.

### 청취 필요 (점수화하지 않음)
- `mood_listen`, `musicality_listen` 열은 모든 행에 `청취 필요` 로 고정한다. **무드 부합과 음악성은 자동 점수를 만들지 않는다.** 청취 루브릭·평가자는 연구 1팀 몫이다.

## 3. 출력

`--out DIR`(기본 `out/evalkit`, `.gitignore` 대상)에 두 파일을 쓴다.
- `results.csv`: 프롬프트별 한 줄. **열 순서: (v0.1 열 그대로) → [v0.2] `provider`, `labels`, 수치 지표의 `<지표>_value`(`tempo_match`, `scale_deviation`, `pitch_range`, `bars_match`, `bars_min`), `axis1_ok`, 별칭 `곡ID`, `언어` → [v0.3] `no_empty_tracks_value`, `midi_instruments_included_value` → [v0.6] `proxy_*` 43개(대리 지표 M1~M7: 판정 `in_range/out_of_range/na`, 사유, 값 열; 5-1절).** 기존 열 이름·순서는 바꾸지 않았고(시험이 고정), 새 열은 모두 끝에 붙는다. 측정 시각 열은 없다.
  - `provider`: 요청한 공급자. `labels`: 라벨이 있는 필드 이름(`;` 구분). `<지표>_value`: 측정한 숫자(템포는 MIDI 의 BPM, 음계 이탈·음역은 비율, 마디는 마디 수), 측정하지 않았으면 빈 칸.
  - `axis1_ok`: 생성에 성공했고 축 1 지표(`midicheck_valid`, `pitch_range`, `note_integrity`, `no_empty_tracks`, `bars_min`)가 모두 pass 또는 na. **1-8 은 분할**한다(연구 1팀 3차 회신): 빈 트랙(`no_empty_tracks`)은 파일 구조 결함이라 축 1 에 두고, 악기 구성(`midi_instruments_included`)만 축 1 에서 빼 축 3(3-7)으로 집계한다. 값은 `no_empty_tracks_value`(빈 트랙 수)·`midi_instruments_included_value`(라벨 악기 중 MIDI 에 있는 비율)에 기록한다. `deterministic` 은 하네스 속성이라 어느 축에도 넣지 않았다.
  - `곡ID`, `언어`: 연구 1팀 제안 이름의 별칭(`id`, `lang` 과 같은 값).
- `summary.md`: 머리에 `evalkit_version`(코드 버전 상수), 세트 이름·크기·파일 해시, 공급자, 폴백, **실행한 허용오차**(템포 기본/옵션 값, 마디 정확 일치, 음계 이탈·음역·길이 임계값), **유효 곡 비율**(생성 성공, `axis1_ok`). 층(A/B/C) × 언어(ko/en) 그룹과 층별·언어별·전체 열, **곡(MIDI) 지표별** `통과/분모 (비율) · na N`, 분모 규칙, **'사양 추출 일치(라벨 ↔ 사양 선언)' 절**(`조성 선언 일치`·`마디 수 선언 일치`·`악기 선언 일치` — 축 1 로 거르지 않고 모든 곡 대상, Intent v1 일치율 지표가 들어올 자리), **2-3 음계 이탈의 라벨 조(tonic+mode)가 있는 항목 수**, **축 1 통과 곡만의 집계**(연구 1팀 규칙: 축 1 실패 곡은 이후 축 2·3 집계에서 뺀다 — `tempo_match`, `time_signature_match`, `midi_instruments_included`, `scale_deviation`), 재시도·폴백·생성 실패 개수, 실패 목록, 읽는 법과 한계.
- **재현성**: 시각·실행 시간·경로를 넣지 않는다. 같은 코드·같은 세트·같은 공급자·같은 허용오차면 두 파일이 바이트 단위로 같다(시험이 확인).

## 4. 공급자
- `rule`: 규칙 공급자(prompt2midi 의 `RuleProvider`).
- `fake`: 모든 프롬프트에 같은 고정 사양(C major, 100 BPM, 4/4, 12마디, 피아노·베이스·드럼)을 돌려주는 시험용. 세트와 무관한 기준선이자 하네스 자체의 시험용이다.
- `llm`: 이 도구는 실행하지 않는다("미실행(키 없음)", 종료 코드 0). 키 등록 이후의 실제 호출은 별도 도구(`tools/live_eval.py` 계획)가 맡는다.

## 5. 확장 지점 (이번 버전에 없음)
- **Intent v1 (문장에서 뽑은 필드의 일치율, 연구 1팀 3-1)**: Intent 스키마가 아직 없어 넣지 않았다. 들어올 자리: `evalkit/metrics.py` 의 `METRICS` 에 새 `Metric` 을 추가하고, `Context` 에 추출된 intent 를 담을 필드를 더하면 된다. `expect` 라벨은 이미 같은 이름(tonic·mode·tempo_bpm·time_signature·bars·instruments)을 쓰므로 추출 일치율과 MIDI 속성 일치율을 **따로** 보고할 수 있다(합의안 4절 위험 1).
- 연구 1팀 26항목 중 '지금 가능' 항목: 번호 대응표를 받으면 이 표에 열을 추가한다.

### 5-1. 대리 지표 M1~M7 (v0.6, 3단계 기준선 P0 — 연구 1팀 정의서 `자동_대리지표_정의.md`)
`src/prompt2midi/evalkit/proxy.py`. M1 선율 반복률·변주, M2 음정 분포, M3 윤곽 다양성, M4 종지음 도착, M5 섹션 간 밀도·음역 차이, M6 코드 간 평균 이동 거리, M7 음계 이탈률. 정의서의 수식·시험 벡터로 구현(`tests/test_proxy.py`).
- **판정 이름은 `in_range / out_of_range / na`** 이며 pass/fail 이 아니다. pass/fail 집계·`axis1_ok` 에 섞지 않는다. CSV 맨 끝에 지표마다 `proxy_<m>`(판정), `proxy_<m>_reason`, `proxy_<m>_<값 이름>`(값, 측정 불가는 빈 칸).
- **임계값은 `proxy.py` 의 `THRESH` 표 한 곳에만 있고 전부 임시값**이다(근거·보정 없음). **청취 상관 검증(곡 30개 이상, Spearman |ρ| ≥ 0.3) 전에는 품질의 근거나 서명 지표로 쓰지 않는다.** 규칙 변경 전/후 비교와 회귀 탐지용이며, 곡의 우열 판정이나 최적화 목표로 쓰지 않는다.
- `midicheck_valid` 또는 `note_integrity` 가 실패한 곡은 전부 `na`(사유 "유효성 실패"). 조는 MIDI 에서 추정하지 않는다(사양의 조, 없으면 세트의 라벨). 섹션·코드 이름은 사양이 있는 우리 출력에서만(M5·M6), 외부 MIDI 는 `na`.
- 우리 `Mode` 7종에 맞춰 `harmonic_minor`(간격 {0,2,3,5,7,8,11}, 3도 3반음·5도 7반음)를 M4·M7 표에 추가했다.
- **M5·M6 보고 규칙(연구 1팀 허지민 제안, v0.7): CSV 는 인접 쌍 최댓값(M5 의 `d_dens`·`d_reg`·`d_range`·`d_vel`), M6 은 평균을 담고, 쌍별·슬롯별 값은 상세 파일 `proxy_details.jsonl` 에 둔다.** 상세 파일은 출력 폴더에 `results.csv`·`summary.md` 와 함께 쓰이며 곡마다 한 줄(JSON, 키 정렬, 시각 없음 — 같은 입력이면 바이트 동일)이다. M5: `sections`(이름, 시작·끝 마디, 밀도, 중앙 음높이, P90−P10, 평균 세기)와 `pairs`(`kind` = `adjacent`(인접) 또는 `return`(재현), 두 섹션 이름, 네 d 값, 인접 쌍은 `contrast`, 재현 쌍은 `close` 판정). M6: `moves`(슬롯 번호, 이전→다음 코드 이름, 시작 tick, `move_pc`, `changed`, 실현 보이싱 `voicing_move`). CSV 의 `return_close` 는 모든 `return` 쌍의 `close` 가 참일 때만 1, `chord_move_pc` 는 `moves` 의 `move_pc` 평균이다(시험이 확인). 재현 쌍은 CSV 최댓값에 섞이지 않는다.
- **정의서 질문 답 반영(v0.8, 연구 1팀 선지우)**: ① **M5 재현 쌍 확정 규칙** — 모든 순번 쌍 `i < j` 에서 `이름_j == 이름_i` 이거나 `이름_j == 이름_i + "2"` 인 경우 전부(예: `A,B,A,B2` → (A,A)·(B,B2) 두 쌍, `A,B,A` → (A,A), `A,A2,A22` → (A,A2)·(A2,A22), `A,A,A` → 세 쌍). ② **재현 쌍의 값은 인접 쌍 최댓값과 별도 열**: CSV 맨 끝 `proxy_m5_ret_d_dens`·`ret_d_reg`·`ret_d_range`·`ret_d_vel`(재현 쌍들의 최댓값, 재현 쌍이 없으면 빈 칸, 쌍별 값은 `proxy_details.jsonl`), `return_close` 는 각 재현 쌍 자체의 값으로 판정. ③ **M4 `section_end_stable`** — 섹션 **안**(시작 마디 ≤ onset < 끝 마디 경계)의 마지막 선율 음을 쓰고, 선율 음이 없는 섹션은 건너뛴다(앞 섹션의 음을 가져가지 않음). ④ **M6 보이싱 트랙 기록** — 어느 트랙에서 읽었는지 `proxy_m6_voicing_track`(`chords` 또는 `pad`, pad 는 chords 역할이 없을 때의 대체로 정의서가 허용) 열과 `reason`·상세 파일에 적는다. 새 CSV 열 5개는 v0.6 의 43열 뒤 맨 끝에 붙었고 기존 열 순서는 그대로다. 정의서 질문 (3)·(4)·(6)~(9) 중 답이 오지 않은 곳은 임시 선택을 유지한다.
- **연구 1팀 참조 값과의 대조(시험)**: 연구 1팀 text2midi 곡 1·5·10(`tests/fixtures/research1_text2midi/`, 라벨 조 사용)의 M1·M2·M3·M4·M7 판정과 모든 값이 참조 구현의 `text2midi10_결과.json` 과 허용오차 1e-3 안에서 일치함을 시험한다(M5·M6 은 참조 값이 없다).
- `deterministic` 은 같은 입력에서 이 지표 값까지 같은지 확인한다. 기존 `scale_deviation`(pass/fail)은 그대로이며 M7 이 대체하지 않는다.
- 이전 PR(#32, v0.5)의 단순 `expr_*` 10개 열은 이 정의서 기준 지표로 **대체**했다(병합 직후라 소비자가 없음). 기준선 값과 해석: `docs/baseline-expressiveness-v0.md`. **이 값을 음악 품질로 보고하지 않는다.**

### 5-2. M5·M6 단위 시험은 어떤 입력으로 되어 있나 (손계산 기대값 사양을 받을 때 옮길 자리)
`tests/test_proxy.py` 의 M5·M6 절과 `tests/test_proxy_details.py`. 입력은 모두 필자가 정의서 수식을 손으로 계산한 값이며, 연구 1팀(선지우)의 손계산 기대값 사양이 오면 같은 형식으로 **교체·추가**한다.
- **M5 입력**: 사양은 4/4, 4마디씩 세 섹션 `A·B·A2`(12마디)이고 선율은 채널 0 음표뿐이다. 섹션 안에서 마디마다 `per_bar` 개의 음을 같은 간격으로 놓고 음높이는 주어진 목록을 돌려 쓴다(세기 기본 80). ① A=[60,62]×4음/마디, B=[67,69]×8음/마디, A2=A → 밀도 4·8·4(마디당), 중앙 음높이 60·67·60, 인접 쌍 두 개의 `d_dens` 0.5·`d_reg` 7, 재현 쌍 A–A2 는 0, `contrast_present` 1·`return_close` 1 → `in_range`. ② 세 섹션이 같음 → `contrast_present` 0 → `out_of_range`. ③ 모양은 같고 세기만 60·80·60 → `d_vel` 20 으로 대비 있음. ④ A=B=[60,62]×4음/마디, A2 만 [80,82]×16음/마디(=멀리 돌아옴) → 재현 쌍 A–A2 의 `d_reg` 20·`close` 거짓(CSV 최댓값에는 인접 쌍 B–A2 만 들어감); 또 A=[60,62]×4, B=[67,69]×8, A2=[72,74]×8 입력에서도 `return_close` 0(`out_of_range`). ⑤ 섹션 1개, 사양 없음 → `na`. ⑥ 재현 쌍 확정 규칙(v0.8): `A,B,A,B2` → (A,A)·(B,B2), `A,B,A`, `A,A2,A22`, `A,A,A`(중복 이름), `X2` 만 있는 경우·`A22`·`A3`·순서가 뒤집힌 경우는 쌍이 아님; 재현 쌍의 값 열(`ret_d_*`)과 `return_close` 가 각 쌍 자체 값으로 정해짐(가까운 쌍 + 먼 쌍이 섞인 `A,B,A,B2`).
- **M6 입력**: 한 섹션 4마디, 마디당 코드 1개(`chords_per_bar` 1), 코드 이름만 바꾸고 선율은 의미 없는 4음. 정의서의 참고 진행 4종(C G Am F = 1.000, Dm7 G7 Cmaj7 Am7 = 0.667, C F G C = 1.333, Am G F E = 1.556)과 단계 값(C→G 1.000, G→Am 1.667, Am→F 0.333, F→C 1.000), 피치클래스 집합(`Bbm7`={1,5,8,10}, `C#dim`={1,4,7}), C→C 0·C→Am 2/3·C→F 1·C→G 1, 같은 코드만 이어진 진행(변화 없음 → `out_of_range`), 코드 2개(`na`), 사양 없음(`na`). 보이싱: 채널 2 의 마디별 삼화음 C=[60,64,67]·F=[60,65,69](이동 1.0)와 넓게 벌린 [48,52,55]↔[65,69,72](한계 4.0 초과).
- **M4 섹션 끝 입력(v0.8)**: 4개 섹션(각 1마디) A·B·C·D, A 는 E(삼화음 구성음)로, B 는 D(아님)로 끝나고 C 에는 선율 음이 없으며 D 에 마지막 C 가 있다 → `section_end_stable` 0.5(이전 코드는 C 가 B 의 D 를 가져가 1/3 이었다). **M6 보이싱**: 채널 2 의 chords 역할과 채널 3 의 pad 대체 각각에서 `voicing_track` 기록.
- **아직 시험하지 않은 것(손계산 기대값이 필요한 곳)**: M5 의 P90−P10 값(최근접 순위 `ceil(q·n)−1`), 섹션 길이가 다른 경우, 선율 음이 아주 적은 섹션의 중앙값, 세기 평균을 섹션별로 낸 값의 정확한 숫자; M6 의 `chords_per_bar` 2, 섹션 경계를 넘는 쌍, 크기가 다른 코드(7화음↔삼화음)의 일대일 대응, `voicing_move` 에서 한쪽이 비어 건너뛰는 쌍. 이 중 정의서 질문 (3)~(9)에 걸린 부분은 선지우 님 답이 올 때까지 현재 임시 선택을 유지한다.

### 7-1. 곡 지표 ↔ 사양 추출 지표 분류 (v0.3, 연구 1팀 2차 회신)

기준: **무엇과 라벨을 비교하나.** 완성된 곡(MIDI)에서 읽은 값이면 *곡 지표*(축 1·2·3), 사양(MusicSpec)에 선언된 값이면 *사양 추출 지표*(문장 → 사양 변환이 라벨을 옮겼는지). 사양 추출 지표는 곡이 깨져도 사양은 맞을 수 있으므로 축 1 통과 여부로 거르지 않고 별도 절에 모은다.

| 지표 | 라벨과 비교하는 값 | 분류 | 판단 근거 | 이동 |
|---|---|---|---|---|
| `tempo_match` (3-3) | MIDI 의 첫 `set_tempo` | 곡 → 축 3 | MIDI 에서 읽는다. 사양 ↔ MIDI 템포 일치는 MidiCheck 가 보장하므로 라벨 ↔ MIDI 는 추출 + 컴파일의 종단 결과 | 없음 |
| `time_signature_match` | MIDI 의 `time_signature` 메타 | 곡 → 축 3 | 위와 같음 | 없음 |
| `scale_deviation` (2-3) | 곡의 음표 ↔ **라벨** 조 음계 | 곡 → 축 2 | 곡의 음을 잰다(조 기준만 라벨) | 없음 |
| `midi_instruments_included` (3-7) | MIDI 프로그램 체인지·드럼 채널 | 곡 → 축 3 | MIDI 에서 읽는다 | 없음 |
| `key_match` | 사양의 `key` 선언 | **사양 추출** | 곡의 조가 아니라 선언값. 2-2 와 다름 | **축 2·3 집계에서 제외**(분리) |
| `bars_match` | 사양의 섹션 마디 합 | **사양 추출** | 사양 값을 센다(사양 ↔ MIDI 길이는 `midicheck_valid` 의 `length_mismatch` 가 덮음 → 3-8) | **이동**(축 3 → 사양 추출) |
| `instruments_included` | 사양의 트랙 악기 | **사양 추출** | 사양 값. MIDI 기준은 `midi_instruments_included` | **이동**(축 3 → 사양 추출) |

이동으로 달라지는 점: 요약에서 `bars_match`, `instruments_included` 도 key_match 와 같은 절에 나온다. CSV 열 이름은 모두 그대로. 3-8(길이·마디 일치)의 '사양 ↔ MIDI' 쪽은 `midicheck_valid`(축 1), '라벨 ↔ 사양' 쪽은 `마디 수 선언 일치`로 나뉜다. **연구 1팀 확인 요청**: `bars_match`·`instruments_included` 이동, `tempo_match`·`time_signature_match` 를 곡 지표로 두는 판단, 3-8 은 3-8a(곡 길이 = 사양 마디, `midicheck_valid`)·3-8b(마디 수 선언 일치, `bars_match`)로 묶어 추적한다. 세 항목 모두 연구 1팀 3차 회신으로 동의 확인.

## 8. `results.csv` 열 ↔ 연구 1팀 제안 형식 (v0.2 적용)

| 연구 1팀 제안 | evalkit 열 | 비고 |
