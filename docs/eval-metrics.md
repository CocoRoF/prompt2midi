# 평가 지표 정의 (evalkit) — 초안 v0

- 상태: **초안. 연구 1팀 서명 대기.** 연구 1팀 `자동채점_항목_정리.md`(26항목) **수령함**(받은 자료/연구 1팀/자동채점_항목_정리.md, 2026-11-11). 그 번호와 이 문서의 지표 이름의 대응은 7절, `results.csv` 열의 대응은 8절. 지금 지표 목록은 합의안(`docs/프롬프트투미디/2단계-계획서-합의안.md` 2절, 8절 '지표 정의 문서')의 "지금 가능" 항목에서 개발 1팀이 먼저 정리한 것이다. 항목 선정·임계값 검토는 연구 1팀, 문서화·구현은 개발 1팀.
- 구현: `src/prompt2midi/evalkit/` · 실행: `python -m prompt2midi.evalkit <세트.json> --provider rule|fake [--out DIR] [--fallback]`
- 외부 데이터·LLM 호출·키 없음. `--provider llm` 은 "미실행(키 없음)"을 출력하고 종료 코드 0 으로 끝난다.

## 1. 평가 세트 형식 (version "1")

JSON Schema: `schemas/evalset.v1.schema.json` (코드의 모델에서 생성, 시험이 일치를 확인). 형식:

```json
{"version": "1", "name": "세트 이름",
 "prompts": [
  {"id": "a01", "lang": "ko|en", "tier": "A|B|C", "text": "프롬프트 문장",
   "expect": {"tonic": "C", "mode": "major", "tempo_bpm": 70, "time_signature": "4/4", "bars": 12, "instruments": ["piano", "drums"]}}
 ]}
```
- `id`: 세트 안에서 유일(`[A-Za-z0-9_.-]`, 64자 이하). `lang`·`tier`는 필수. 층(A/B/C)의 뜻은 세트 작성자(연구 1팀)가 정한다 — 하네스는 집계 단위로만 쓴다.
- `expect`(정답 라벨)는 **프롬프트에 글자로 적힌 속성만** 넣는다. 전부 선택이다. 라벨이 없는 항목은 그 지표가 **`na`(해당 없음)** 가 되어 분모에서 빠진다. 무드·장르·음악성은 라벨 필드가 없다(자동 채점 대상이 아님).
- `tonic`은 사양의 `Tonic` 값(이명동음 `C#`/`Db`는 같은 음으로 비교), `mode`는 `Mode` 값, `instruments`는 사양의 `Instrument` 값 + `drums`.
- 알 수 없는 필드, 범위 밖 값, 중복 id, 빈 세트는 **거부**한다(종료 코드 2, 문제 목록 출력).
- **보류 세트**: 개발 1팀은 보류분을 열지 않는다(합의안 8절). 하네스는 세트 **파일 경로를 인자로 받을 뿐**이며 보류 파일을 레포에 두지 않는다. `.gitignore` 에 `data/eval/holdout*` 가 들어 있어 실수로 올라가는 것을 막는다. 최종 점수는 1회만 잰다(연구 1팀 규칙).

## 2. 지표 (pass / fail / na)

모든 지표는 `pass`, `fail`, `na` 와 사유 문자열을 낸다. **집계의 분모 = pass + fail.** `na` 는 분모에서 빼고 따로 개수만 적는다. 생성 자체가 실패한 프롬프트는 라벨이 있는 지표와 유효성 지표에서 `fail`(사유 "생성 실패")이다 — 시스템이 요구를 못 채운 것이므로 분모에 남긴다. 라벨이 없으면 생성이 실패해도 `na`.

| 지표 (코드 이름) | 무엇을 보나 | 합격 판정 | 해당 없음(na) | 한계 |
|---|---|---|---|---|
| 템포 일치 `tempo_match` | MIDI 첫 `set_tempo` 의 BPM 과 `expect.tempo_bpm` | 차이 ≤ 0.5 BPM | 라벨 없음 | 곡 중간 템포 변화는 보지 않음. 라벨은 정수 BPM |
| 조성 일치 `key_match` | **사양에 선언된** 조성(`key.tonic`, `key.mode`)과 라벨 | 라벨이 있는 필드(tonic, mode)가 모두 일치. tonic 은 이명동음 동일 처리 | tonic·mode 둘 다 없음 | 생성된 음을 분석한 조성이 아니라 선언값이다(컴파일러가 선언 음계 안에서만 쓰는 구조의 효과). text2midi 의 '자동 추정'과 같은 조건이 아님 |
| 박자표 일치 `time_signature_match` | MIDI 첫 `time_signature` 메타와 라벨(`"4/4"`) | 문자열 동일 | 라벨 없음 | 박자 변화는 보지 않음 |
| 마디 수 일치 `bars_match` | 사양의 전체 마디 수(섹션 합)와 `expect.bars` | 동일 | 라벨 없음 | 반복·인트로 등 구조 해석은 하지 않음 |
| 길이 규칙 `bars_min` | bars 를 **명시하지 않은** 프롬프트의 마디 수 | ≥ 8마디 (합의안 Q3: 기본 12, 최소 8). 12 와 다르면 사유에 "(기본 12마디와 다름)"만 적고 판정은 8 기준 | bars 라벨이 있는 프롬프트(그쪽은 `bars_match`) | 초 단위 길이는 템포·박자에 따라 달라 이 지표에 넣지 않음 |
| 악기 포함 `instruments_included` | 라벨 악기가 사양 트랙의 악기(`drums` 는 드럼 트랙 존재)에 모두 들어 있나 | 라벨의 모든 항목이 존재 | 라벨 없음 | **사양 기준**이다. MIDI 프로그램 번호를 직접 읽지는 않음. 라벨에 없는 악기가 더 있어도 감점하지 않음 |
| 악기 포함(MIDI) `midi_instruments_included` | 라벨 악기가 **MIDI 의 프로그램 체인지**(음이 있는 채널)와 드럼 채널에 모두 있나. 연구 1팀 3-7 | 라벨의 모든 항목이 존재 | 라벨 없음 | 프로그램 번호→악기는 17종 GM 매핑만. 같은 프로그램을 쓰는 다른 악기는 구분 못 함 |
| 음계 이탈음 `scale_deviation` | **라벨의** 조(tonic+mode) 음계 밖 음표 비율(드럼 채널 제외). 연구 1팀 2-3 | ≤ 10% | tonic·mode 라벨 중 하나라도 없음, 음높이 있는 음표 없음 | 경과음·장식음 감안 없음(모든 음표 동일 가중). 재즈·블루스 25% 완화 규칙은 장르 라벨이 없어 미적용. 라벨 조가 틀리면 실패하므로 `key_match` 와 함께 읽는다 |
| 악기 음역 `pitch_range` | 악기(채널의 GM 프로그램)별 음역 밖 음표 비율. 연구 1팀 1-2 | ≤ 5% | 음높이 있는 음표 없음 | 음역표(`INSTRUMENT_RANGE`)의 일부 값은 출처 미확인 근사다(spec.py 주석). 0~127 범위는 파서가 먼저 거른다(1-1) |
| 음 짝·길이 `note_integrity` | NoteOn/NoteOff 짝, 길이 0 음, 닫히지 않은 음, 깨진 트랙. 연구 1팀 1-3 | 위반 0개 | 없음 | MidiCheck 는 길이 0 음을 *경고*로만 보므로 여기서 실패로 센다. 벨로시티 1~127 은 파서가 0~127 밖을 받지 않아 별도 검사 없음 |
| 빈 트랙 없음 `no_empty_tracks` | 템포·박자 트랙이 아닌데 음표가 없는 트랙. 연구 1팀 1-8 | 0개 | 없음 | 트랙 이름·역할까지는 보지 않음 |
| MidiCheck 유효 `midicheck_valid` | 생성된 MIDI 에 `check_midi` **오류** 0건(경고 제외). 파싱·헤더, 템포·박자표 이벤트 존재와 사양 일치, 길이가 사양 마디와 일치, 드럼 채널 일치를 포함 | 오류 0건 | 없음(항상 적용) | 구조 유효성이지 음악적 타당성이 아님 |
| 결정성 `deterministic` | 같은 입력·같은 공급자로 2회 생성한 MIDI 바이트 동일 | 동일 | 생성 실패(비교할 바이트 없음) | 같은 프로세스·같은 의존성 버전 안에서의 확인. 다른 해시 시드 프로세스는 `tests/test_compiler.py` 가 따로 본다 |

### 참고 열 (합격 판정 아님)
- `attempts`, `retries`(= 시도 − 1), `fallback_used`: 재시도·폴백 여부. 요약에는 그룹별 개수만 적는다. 기본은 폴백 **끔**이라 숫자가 선택한 공급자 단독의 성능이다(`--fallback` 으로 켬).
- `generated`, `error`, `bars`, `midi_sha8`, `provider_used`.

### 청취 필요 (점수화하지 않음)
- `mood_listen`, `musicality_listen` 열은 모든 행에 `청취 필요` 로 고정한다. **무드 부합과 음악성은 자동 점수를 만들지 않는다.** 청취 루브릭·평가자는 연구 1팀 몫이다.

## 3. 출력

`--out DIR`(기본 `out/evalkit`, `.gitignore` 대상)에 두 파일을 쓴다.
- `results.csv`: 프롬프트별 한 줄. 지표마다 `이름`, `이름_reason` 두 열.
- `summary.md`: 층(A/B/C) × 언어(ko/en) 그룹과 층별·언어별·전체 열, 지표별 `통과/분모 (비율) · na N`, 재시도·폴백·생성 실패 개수, 실패 목록, 읽는 법과 한계. **분모 규칙을 요약 안에 적는다.**
- **재현성**: 시각·실행 시간·경로를 넣지 않는다. 같은 코드·같은 세트·같은 공급자면 두 파일이 바이트 단위로 같다(시험이 확인).

## 4. 공급자
- `rule`: 규칙 공급자(prompt2midi 의 `RuleProvider`).
- `fake`: 모든 프롬프트에 같은 고정 사양(C major, 100 BPM, 4/4, 12마디, 피아노·베이스·드럼)을 돌려주는 시험용. 세트와 무관한 기준선이자 하네스 자체의 시험용이다.
- `llm`: 이 도구는 실행하지 않는다("미실행(키 없음)", 종료 코드 0). 키 등록 이후의 실제 호출은 별도 도구(`tools/live_eval.py` 계획)가 맡는다.

## 5. 확장 지점 (이번 버전에 없음)
- **Intent v1 (문장에서 뽑은 필드의 일치율, 연구 1팀 3-1)**: Intent 스키마가 아직 없어 넣지 않았다. 들어올 자리: `evalkit/metrics.py` 의 `METRICS` 에 새 `Metric` 을 추가하고, `Context` 에 추출된 intent 를 담을 필드를 더하면 된다. `expect` 라벨은 이미 같은 이름(tonic·mode·tempo_bpm·time_signature·bars·instruments)을 쓰므로 추출 일치율과 MIDI 속성 일치율을 **따로** 보고할 수 있다(합의안 4절 위험 1).
- 연구 1팀 26항목 중 '지금 가능' 항목: 번호 대응표를 받으면 이 표에 열을 추가한다.

## 6. 연구 1팀 확인 사항 (서명 대기)
1. 위 지표 이름·합격 판정(특히 템포 허용 ±0.5 BPM, 조성은 선언값 기준, `bars_min` 기준 8마디)에 동의하는가.
2. `expect` 라벨 필드 목록이 세트 정답 라벨과 맞는가(`instruments` 값은 사양의 17종 + `drums`).
3. 층 A/B/C 의 정의(하네스는 집계 단위로만 사용).
4. 7절 대응표의 '덮임/별도 지표/대기/na' 구분과 8절 열 대응(별칭 열 제안)에 동의하는가.
5. 템포 합격 허용: 연구 1팀 3-3 은 ±10%, evalkit `tempo_match` 는 ±0.5 BPM(규칙 공급자는 명시값을 그대로 쓰므로 엄격). 신경망 공급자(text2midi 등)를 같은 하네스로 잴 때 ±10% 를 쓸지.
6. 서명: 연구 1팀 ______ (날짜 ______)

## 7. 연구 1팀 26항목 ↔ evalkit 지표 대응표

출처: `받은 자료/연구 1팀/자동채점_항목_정리.md`(항목 번호·실행 단계)와 `평가_기준_초안.md`(항목 정의, 배채린 2026-11-10). 범례: **구현됨** = evalkit 지표가 채점 / **덮임** = 별도 지표 없이 `midicheck_valid`(MidiCheck 오류)가 이미 잡음 / **na** = 규칙 공급자에는 해당 없음 / **대기** = 선행 조건 필요(조건 명시) / **청취 전용**. 합격선은 연구 1팀 제안값 그대로 표기하고, evalkit 값이 다르면 비고에 적는다.

| 번호 | 항목 | 상태 | evalkit 지표 | 비고 |
|---|---|---|---|---|

| 1-2 | 음 범위 | **구현됨** | `pitch_range` | 악기 음역 밖 ≤ 5%. 0~127 밖은 파서가 거름. 음역표 일부 근사(한계 참고) |
| 1-3 | 박자·길이 값 | **구현됨** | `note_integrity` (+ `midicheck_valid`) | MidiCheck 는 짝 불일치·미종료 음을 오류로 잡지만 길이 0 음은 경고뿐이라 별도 지표로 보강. 벨로시티는 파서 단계에서 보장 |
| 1-4 | 최소 길이 | **덮임 + 구현됨** | `midicheck_valid`(MIDI 길이 = 사양 마디, 허용오차 0) + `bars_min`(≥ 8마디) | 합의안 Q3 에 따라 **초가 아니라 마디 기준**(연구 1팀 초안의 '30초 또는 8마디' 중 8마디만 채택). ±10% 허용은 쓰지 않고 더 엄격하게 정확 일치 |
| 1-5 | 템포·박자표 이벤트 존재 | **덮임** | `midicheck_valid` (+ `tempo_match`, `time_signature_match`) | `tempo_missing`, `signature_missing`, `*_late`(0틱이 아님)와 사양 불일치를 오류로 처리 |
| 1-6 | 끝맺음 도달(EOS) | **na**(규칙 공급자) | — | 신경망 토큰 생성용 항목. 컴파일러는 사양 마디 끝까지 쓰고 `midicheck_valid` 가 길이·`note_past_end` 를 확인 |
| 1-7 | 재생 가능성(사운드폰트 렌더) | **대기** ⚖ | — | 사운드폰트 선정과 라이선스 확인 전에는 구현·내려받기 안 함 |
| 1-8 | 트랙·악기 구성 | **구현됨** | `no_empty_tracks` + `midi_instruments_included` (+ `instruments_included` 사양 기준) | 빈 트랙 0 + 요청 악기가 프로그램 체인지에 존재 |

### 축 2 — 음악 이론 부합
| 번호 | 항목 | 상태 | evalkit 지표 | 비고 |
|---|---|---|---|---|
| 2-1 | 조 추정 신뢰도(선행 게이트) | **대기** | — | 사람이 단 정답 조 20곡(배채린 라벨) + 추정기 2종 |
| 2-2 | 조 일치(사양 조 vs 곡의 조) | **대기**(2-1 통과 뒤) | (관련: `key_match`) | `key_match` 는 *라벨 ↔ 사양 선언값* 비교라 2-2(사양 ↔ 곡에서 추정한 조)의 대체가 아니다. 규칙 공급자에서는 구조상 거의 항상 통과 |

## 8. `results.csv` 열 ↔ 연구 1팀 제안 형식

연구 1팀 제안(`자동채점_항목_정리.md` 2절): `곡ID, 언어, 모델, 조건 유무, 항목별 값, 통과 여부, 측정 시각`. **측정 시각은 재현성 때문에 넣지 않는다**(같은 코드·같은 세트면 바이트 동일, 결정 유지). 이름은 **바꾸지 않았다.** 아래는 대응과 제안이다(연구 1팀 확인 전).

| 연구 1팀 제안 | evalkit 열 | 대응 | 제안(확인 뒤에 적용) |
|---|---|---|---|
| 곡ID | `id` | 같은 뜻 | 별칭 불필요, 문서에 대응만 기재 |
| 언어 | `lang` | 같은 뜻(`ko`/`en`) | 〃 |
| (층) | `tier` | 연구 1팀 제안에 없음 | 유지 |
| 모델(공급자) | `provider_used` (요청한 공급자는 요약 머리말) | 폴백이 있으면 실제 사용 공급자, 생성 실패면 빈 칸 | **`provider`(요청한 공급자) 열 추가**를 제안 |
| 조건 유무 | (별도 열 없음) 각 지표의 `na` | 라벨이 있어야 채점하므로 `na` 가 '조건 없음'을 뜻한다 | `labels`(라벨이 있는 필드 목록) 열 추가를 제안 |
| 항목별 값 | `<지표>_reason` (사유 문자열 안에 값이 있음, 예 `MIDI 100.00 BPM, 라벨 120`) | 값이 문장 속에 있어 기계가 읽기 어렵다 | 수치 지표(템포·음계 이탈·음역·마디)에 `<지표>_value` 숫자 열 추가를 제안 |
| 통과 여부 | `<지표>` (`pass`/`fail`/`na`) | 지표마다 3값 | 곡 단위 종합 '통과 여부'는 없다. 연구 1팀 규칙(축 1 하나라도 실패하면 이후 축 제외)을 따를 `axis1_ok` 열 추가를 제안 |
| 측정 시각 | — | **의도적으로 없음** | 시각 대신 `summary.md` 에 세트 파일 sha256 앞 8자를 적고 있음. 도구 버전은 `evalkit_version` 을 요약에 넣는 것을 제안(시각 아님) |
| (유효 곡 비율) | `generated` + 요약의 '생성 실패' | 연구 1팀 2절 '축 1 실패 곡은 이후 집계에서 뺀다'는 아직 미구현 | 요약에 '유효 곡 비율'과 '축 1 통과 곡만의 집계' 추가를 제안 |

호환 방식 제안: 열 이름은 그대로 두고 **별칭 열을 끝에 추가**(예: `곡ID`, `언어`)하거나, 이름 대응은 이 표로만 문서화한다. 둘 중 연구 1팀이 고르면 적용한다.
